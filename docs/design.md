# sa3BrowserDaw design

A proof-of-concept phone DAW that runs entirely in the browser. Stable Audio 3 (SA3) generates instrument samples on the device; a piano roll plays them chromatically. Shared with other people via a page hosted on the Steam Deck.

Basis: `/home/deck/SketchBook/Projects/PocketDaw/docs/sa3-browser-poc.md` and the working PoC at `/home/deck/Documents/Codex/sa3-browser-poc` (worker code, sampler maths, GPU probe). Layout follows the PocketDaw mockups (`PocketDaw/docs/mockups/`): bottom sheets, a visible button for every action, portrait only. Visual style and component setup follow `/home/deck/SketchBook/Projects/AstraMoode/AstraCamillaGui/client` (Svelte 5, Vite, Vitest, `styles/theme.css` tokens, `KnobDial`, `HSlider`, `Nav`, icon set): copy and adapt what is needed; PocketDaw's orange accent is used for transport and the SA3 violet for generation actions.

## Confirmed requirements

- Tracks, each with one looping piano-roll pattern (1-4 bars) and one instrument sample.
- Instrument sample = SA3 output: prompt such as "synth lead" generates a short single-note sound. The app detects its pitch (root note), trims silence, and plays it at other notes by changing playback rate (sampler). Generation has three types: Sample (one-shot), Instrument (resynthesized, tuned) and Looped (the source audio with a seamless loop in its sustained part, so held notes sustain; see `docs/instruments.md`). Only Looped has loop points, found automatically; there is no manual loop editing.
- Single generation, auto-kept on the track; regenerate replaces it. Root note is shown and adjustable by semitone buttons.
- Melodies are hand-drawn on the piano roll. No random-melody button.
- The Mix screen has horizontal channel strips with volume, pan, Mute/Solo, stereo meters and ordered EQ/Reverb inserts (up to six per track). Master has volume and a stereo meter.
- Models, user-selectable: Small Music (Q4, about 683 MB with the shared encoder), Small SFX and Medium (about 2.29 GB). Medium is unverified on phones. No browser-ready Small SFX export exists yet: the community Q4 export covers Small Music only and the official SFX ONNX is large (about 1.8 GB DiT in bf16). A Small SFX pack must be produced by converting that export the way the PoC converted Medium (task 5); until the pack exists, the SFX choice shows as not available.
- Model files install with one Download button per model into browser storage (Cache Storage). The user is never asked to pick a folder or import a file.
- Models download once into browser storage (persistent storage requested) and are never refetched while stored. The app shell, runtime, models, project and generated audio all work with no network after the first visit.
- Whole project (tracks, notes, tempo, key, samples) autosaves and reloads on the next visit.
- Hosting: LAN, self-signed HTTPS (WebGPU needs a secure context). Others on the LAN accept a certificate warning once.
- Startup compatibility verdict that says whether the app runs in this browser and, when not, why. Debug screen with live log and reports.

## Not in scope

Export to WAV, arrangement of multiple clips, manual loop-point editing, recording, MIDI, tunnelled/public hosting, accounts, inference on a server this project hosts.

## Architecture

Vite + TypeScript + Svelte 5 SPA; Vitest for logic tests. Production build is static files under `dist/`. `server/serve.mjs` serves `dist/` and `/models/` over HTTPS (self-signed cert in ignored `certs/`) with an HTTP port for local use. It runs no inference. Optional cloud generation calls Stability AI's Stable Audio 3 API (`src/gen/cloud.ts`) directly from the browser with a key the user pastes on the Models screen; the key lives only in that browser's localStorage (`sa3daw.stabilityKey`).

```
src/
  app/        Svelte UI: screens, sheets, components, theme (css)
  audio/      AudioContext, sample voice, scheduler, pitch detection, sample prep
  gen/        SA3 generation: main-thread client + module worker (ported from the PoC)
  store/      project model, IndexedDB persistence, model manager (Cache Storage), storage persistence
  transcribe/ piano transcription: windows, note extraction, resampling, worker + client
  compat/     capability probes and verdict rules
  log/        ring-buffer logger, report builder
public/       ort/ (ONNX Runtime WASM), gpu-probe.onnx, icons, manifest, service worker source
models/       ignored; links to PoC model files; manifest.json generated by script
```

### Models and offline storage

- `scripts/make-manifest.mjs` writes `models/manifest.json`: packs with file lists and byte sizes. Packs: `encoder` (tokenizer + text_encoder_q4, shared), `small-music` (number_conditioner, dit_q4, decoder_q4), `small-sfx` (same layout, converted per task 5; listed only when its files exist), `medium` (dit_q4, decoder_fp16 from `models-medium`), `piano-transcriber` (one ONNX, no requirements, listed only when `models/piano-transcriber/` exists). Each SA3 model = encoder + its own pack. The unused FP16 diffusion graph and `dec_fp16.onnx` are never packaged.
- Model manager downloads each file with progress, verifies byte size, writes to Cache Storage (`sa3-models-v1`), calls `navigator.storage.persist()`, reports `navigator.storage.estimate()`. A pack is "installed" only when all files are present and sized correctly. Delete per pack. Resumable at file granularity.
- Generation worker reads files from Cache Storage; it never hits the network for model files once installed.
- The loaded SA3 sessions stay resident in the worker between generations (Small: all sessions; Medium: sessions are released between stages as in the PoC to limit memory). A "Free model memory" button unloads them.
- A service worker precaches the app shell and ONNX Runtime WASM so the page opens offline. It adds `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` to responses it serves. WASM thread count: 1 on Android and whenever not cross-origin isolated, otherwise up to 4 (as in the PoC).

### Piano transcriber

- Model: ByteDance "High-resolution Piano Transcription", note model only (no pedal), exported to ONNX with fp16 weights and an fp32 front-end (58.3 MB, file `piano-transcriber/piano_note_fp16.onnx`). Input `audio` [B, 160000] float32 at 16 kHz, dynamic batch; outputs `reg_onset_output`, `reg_offset_output`, `frame_output`, `velocity_output`, each [B, 1001, 88]. On six test takes the note list of the fp16 model agreed with the fp32 model (spike measurement, not re-run in this repo).
- Pack `piano-transcriber`, label "Piano transcriber (ByteDance)", no required packs, so it installs and deletes without the text encoder. The Models screen card shows size, Download / Resume / Delete, progress and the credit line "Piano transcription model by Qiuqiang Kong et al. (ByteDance), CC BY 4.0, https://zenodo.org/records/4034264". Deleting the pack, Delete all models, Clear all app data and Free model memory end the transcription worker.
- Pipeline (replicates `piano_transcription_inference`): mono 16 kHz audio gets 1 s of silence in front and a tail pad to a multiple of 160000 samples; 10 s windows with a 5 s hop run one at a time; `deframe` drops each window's last frame and keeps frames 0-75 % of the first window, 25-75 % of inner windows and 25-100 % of the last; notes come from onset/offset regression peaks (thresholds 0.3 / 0.3, frame threshold 0.1, 2 and 4 neighbour frames), the offset by the frame threshold or the offset peak, velocity `trunc(v * 128)`; times shift back by the pad and notes ending inside the pad are dropped. Test: the exact head arrays of one take (quantised to 3 decimals, sparse) give the same 25 notes the Python package computes from those arrays; the real UI given the reference 16 kHz audio of all six takes gives the same note counts (25, 35, 43, 39, 27, 62) and the same first 40 notes as the spike.
- Audio input: the Debug screen reads a chosen audio file on the main thread. A WAV file is decoded at its own sample rate and resampled by a Kaiser-windowed sinc; other formats are decoded by the browser at 16 kHz. Note counts react to the resampler on the synthetic SA3 takes (see `docs/handoff.md`), so resampling accuracy against librosa is "to check" with real recordings.
- Runtime: a module worker (`src/transcribe/worker.ts`) creates one onnxruntime-web WASM (CPU) session from the model bytes in Cache Storage and reuses it. Threads: 1 when the page is not cross-origin isolated, else min(4, cores); the Debug screen offers Auto, 1, 2 and 4, and a changed choice starts a new worker (the WASM runtime reads its thread count once). The result shows duration, note count, total time, real-time factor, model load, per-window times, threads, `crossOriginIsolated`, and the first 40 notes; Play notes sounds them as triangle-wave tones (the sample and instrument engine has no plain pitched voice). The report holds the last run and error under `pianoTranscriber`.
- Cross-origin isolation: `server/serve.mjs`, `server/nginx.conf` and the service worker already send `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`. Models fetched cross-origin from Hugging Face use `mode: 'cors'`, which `require-corp` allows without a CORP header; headless Chromium confirmed `crossOriginIsolated` true, a cross-origin CORS install of the model from a second local origin, and the service worker and offline reload working. The headers are unchanged. Whether Hugging Face's CORS response behaves the same is "to check" after upload.

### Compatibility verdict

`compat/` returns `{verdict: 'ok' | 'maybe' | 'no', checks: [{id, label, status, detail}]}`. Checks: secure context; WebGPU API; adapter obtained; `shader-f16`; max storage buffer binding >= 128 MiB; tiny ONNX WebGPU probe passes within 60 s; module workers; Cache Storage and IndexedDB; storage quota vs chosen pack size; `navigator.deviceMemory` when exposed; Web Audio; user-agent family (iOS/iPadOS WebKit flagged `maybe` with the reason: WebGPU and memory limits unverified, to check). `no` = a hard requirement failed (reason shown in plain words). `maybe` = runs but something is unverified or marginal; user may continue. The result screen has Copy report. Verified-device notes live in `docs/compat.md`; unverified entries are marked "to check".

### Audio

- `sample prep`: stereo WAV from SA3 → mono Float32 at 44.1 kHz, trim leading/trailing silence, short fade-out, normalize; stored as Float32 PCM in IndexedDB per track.
- `pitch detection`: autocorrelation or YIN on the sustained region; returns MIDI note (fractional) + confidence; low confidence falls back to C4 and is flagged in the UI.
- `voice`: `AudioBufferSourceNode` with `playbackRate = 2^((note - root)/12)`, gain envelope (short attack, release at note end). Notes longer than the sample end with the sample. A looped sample sets `loop`, `loopStart` and `loopEnd` (buffer seconds, not scaled by the rate) and sounds until its note ends. `src/audio/loopPoints.ts` finds and bakes the loop; the Chop view edits only the kept region, and a chop that reaches into the loop plays the sound as a one-shot.
- `scheduler`: look-ahead scheduler over the pattern loop at the project tempo; a play-head position for the UI; notes starting while playing or auditioned from the piano keys.
- Generation prompt template: `"<user prompt>, single sustained note, dry, no reverb, no drums"`.

### Project model and persistence

`Project {id, name, bpm, key, bars(1-4), tracks[]}`, `Track {id, name, muted, sampleId|null, rootMidi, notes[{id, midi, start(16ths), length}]}`. Notes snap to 1/16. Autosave on change (debounced 500 ms) to IndexedDB; samples stored separately by id (a looped sample stores its loop region in seconds; `Track.soundType` is `sample`, `instrument` or `loop`). Load on start; "New project" and "Delete project" buttons with confirmation. One project slot for the demo.

### Screens (portrait, 412 px design width)

1. Compatibility gate: verdict, per-check list, Continue / Copy report / Open Debug.
2. Tracks (home): header with project name, readouts (position, tempo, key, bars), track rows (name, mute, root note, waveform thumbnail, Open roll, Generate), Add track; transport bar (stop, play, loop indicator); bottom nav: Tracks · Mix · Models · Debug.
3. Piano roll: note grid with piano-key column, visible tools (Draw, Erase), length -/+, transpose -/+ for selected note, Delete, Clear, grid is 1/16; tap key = audition; playhead; back button. A Chords chip (hidden by default) shows one row of seven buttons for the project's key, roman numeral plus chord name (I C, ii Dm, … vii° B°; natural minor for a minor key). Tapping one places the triad at the cursor with the current note length and velocity, voiced near the cursor pitch inside MIDI 24..96, plays each note once, and shows "Placed Dm · 3 notes" in the info line; the cursor stays where it is. Undo removes the whole chord; its notes edit like any others.
4. Generate sheet: On device / Cloud source switch (Cloud is disabled until a key is saved; Cloud hides the model and processor choices, limits steps to 4 to 8, length to 1 to 12 s, and shows the 8-credit cost), Sound type switch (Sample, Instrument, Looped; each remembers its own length and steps), prompt, quick-prompt chips, model (Small SFX / Small Music / Medium, shows installed state), length 2/3/4 s, steps (default 8; on-device up to 64, cloud up to 8), seed (random button), Generate with violet button; progress with stage names and elapsed time; Cancel; result shows waveform, detected root, ±1 semitone, Play, Re-generate.
5. Models: per-model size, installed state, Download / Delete (confirmation), progress, persistence status, storage usage, Free model memory, Delete all models, Clear all app data (models, project, samples, saved cloud key; confirmation). A Cloud generation section holds the key field (password type), Save and Clear buttons and a masked-key state line. Nothing is stored until the user taps Download. The shared encoder is removed with the last model that needs it.
6. Debug: level-filtered live log; Piano transcriber section (Choose file, Run, Cancel, Threads, Free transcriber memory, result, note table, Play notes; a Download button opens Models when the pack is missing); GPU adapter info and limits; storage estimate; per-generation timing table (load, conditioning, each step, decode, prep); Copy report, Download report (JSON), Clear.

### Logging

Every module logs through `log/`: `{t, level, scope, message, data?}` in a ring buffer (5000 entries), also mirrored to `console`. Worker messages carry log entries and stage timings. Uncaught errors and unhandled rejections are captured. The report JSON contains: app version/build time, user agent, compat verdict + checks, GPU info, storage estimate, installed packs, last 5 generation timing records, and the log.

## Verification

- Vitest and svelte-check: pitch detection on synthesized tones, sample prep, playback-rate maths, scheduler timing with a fake clock, project persistence round trip (fake IndexedDB), compat verdict rules with fake environments, manifest/pack install state, log ring buffer and report.

Phone behavior is checked by the user.
- Targets: Linux Chrome on the Deck (verified by smoke); Android Chrome on a Pixel 10 Pro XL (user-reported working for the PoC, to confirm for this app). iOS/Safari and other phones: to check; the app reports its own verdict.
